## Open issues for review

**RS-6** (GC-7, from F-8) — neither `CFG_PATH.read_text()` nor the `json.dumps(..., ensure_ascii=False)`
stdout write names an encoding, so on a `C`/`POSIX`-locale host at the documented Python 3.6 floor a
valid document with a non-ASCII tag can be reported as unreadable on the read **and** can die on the
write. It is a pre-existing repo-wide class (`load_nodes()`, `load_settings()`, `_load_lang()`,
`cmd_ls`), the read failure is caught as `(OSError, ValueError)` and rendered as one sentence rather
than a traceback, and per D-6 this task follows the repo's `read_text()`-with-no-argument convention.
No code was bought for it here.

`parse_tuic()` silently drops the tuic password: `urllib.parse.urlparse().username` stops at the
`:`, so `":" in userinfo` at `bin/sc:713` is never true for a `tuic://uuid:password@host` link and
the emitted outbound always carries `"password": ""`. Found while building V-1's fixture (the
control read could not find the tuic password on disk because it never reached disk). Pre-existing,
unrelated to T-06, out of this task's scope — worth a pool row.

A consequence of the above, visible in this feature's output: a credential key whose value is the
empty string still renders `******`, so an *unset* credential is indistinguishable from a set one.
That is FR-5 as written (the value is replaced whatever its type) and no code was written against
it; flagged so the reviewer sees it was a decision, not an accident.

`RS-3` and `RS-4` from the design (the two-inode provenance window, and `json.loads` keeping the last
of duplicate keys) are unchanged by the implementation and still travel to stages 5 and 6.
