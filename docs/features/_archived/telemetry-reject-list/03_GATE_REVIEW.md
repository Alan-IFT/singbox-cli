## Pre-answered developer questions

| id | question | answer |
|---|---|---|
| D-1 | Gate condition GC-1 — is there a **smaller** design than the one stage 2 chose? | No, in code; yes, in published surface. Four smaller shapes were tested against the file, not accepted on assertion: (0) putting the rule in `CONFIG_BASE` and dropping `_telemetry_overlay()` is **not expressible** — `DIRECTIVES` (`sc:1089`) has no removal member, so `allow` could only be reached by `$replace`ing the whole array, which is the configuration literal AC-8 forbids; (a) fusing `_telemetry_overlay()` with `_dns_overlay()` is **not expressible** — `_directive_of` (`sc:1206-1219`) raises on one merge-value object carrying two `$` keys, the two rules need different positions from different inputs, and the only fusion left (one function returning two overlays) edits a symbol K-6/AC-7 freeze while removing nothing; (b) inlining `_telemetry_setting()` **loses** — it has two consumers, one of which calls it twice for the before/after comparison, so inlining creates two derivations of "absent means block" and two bad-value lines, the duplicated judgment rule 85 names, and makes FR-6/AC-6 unverifiable; (c) the list is data, not machinery, and 18 ≤ 24 with four classes is right — the correct shrink is not "fewer names" but "no name the project cannot evidence" (C-3). Rule 85's new clause landed after stage 2 ran, so stage 2 naming only *larger* rejected alternatives is not a finding; this gate performed the smaller-direction test in its place, and the one place the design is genuinely larger than it needs to be is F-2 — two published anchors, one of which exists in only one state, which is diff-invisible cost that every future reader and every user must hold. |
