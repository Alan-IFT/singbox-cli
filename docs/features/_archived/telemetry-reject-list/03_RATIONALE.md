## GC-1 — the "less is more" test, run in the smaller direction

The clause puts the burden of proof on the larger design and tells stage 3 to *test* stage 2's answer. Stage 2's answer is about two **larger** alternatives (a `_setting_reader()` factoring, a generalised list-of-names overlay), which discharges the counter-rule but not this clause, so the test below is this gate's, not stage 2's. Rule 85 gained its `## Less is more` section after stage 2 ran, which is why no finding is filed against stage 2 for not naming a smaller alternative.

**Candidate 0 — no overlay at all: the rule in `CONFIG_BASE`, removed under `allow`.** This is the smallest conceivable shape (data, no function) and it is the one nobody named. It fails on the file: `DIRECTIVES` (`sc:1089`) is `$prepend / $append / $replace / $before / $after` — there is no removal member, and `_apply_directive` (`sc:1245-1270`) has no branch that shortens an array. Reaching `allow` would need `$replace` carrying the whole surviving array, which is a configuration literal (AC-8), re-states the base's `dns.rules` in a second place (out-of-scope item 1's exact hazard) and interacts with `_filter_rules`'s degradation. Not available, and not available for a reason K-7/FR-10 forbid removing.

**Candidate (a) — one overlay function for T-16's rule and T-17's.** Also not available. `_directive_of` (`sc:1206-1219`) raises `cannot be combined with other keys in the same object` when a merge value carries two `$` keys, so `{"$prepend": [...], "$before": {...}}` at `dns.rules` is a hard error — the dispatch asked me to check this rather than assume it, and the check is `len(keys) > 1` at `sc:1209`. The remaining fusions each cost more than they save: one function returning a *list* of two overlays edits `_dns_overlay()`, which K-6 and AC-7 freeze and whose docstring states index 0 as a contract; and a single `$prepend` carrying both rules would put the reject rule ahead of the `hosts_dns` rule (BC-11) or behind T-16's (FR-11). Two sibling functions with one reader each is the smaller shape once the constraints are counted, and `docs/dev-map.md:57` already records the same sibling-not-extension argument for `_dns_overlay` vs `_runtime_overlay`.

**Candidate (b) — inline `_telemetry_setting()`.** Declined. It has two consumers, and `cmd_telemetry()` calls it twice (before and after the save), so inlining creates three derivations of "absent means block" and three places the BC-5 stderr line could be spelled — the duplicated-judgment defect rule 85 names in its own test 2 — and it makes FR-6's "exactly one function is the definition" and AC-6's deletion test unverifiable. The function is ~12 lines mirroring `_ipv6_setting()` (`sc:1439-1465`) verbatim, so a future reader holds one shape, not two.

**Candidate (c) — a shorter list.** The list is data an existing mechanism consumes, which is the shape rule 85 prefers; its size is not machinery. But rule 85 also says count what every future reader must hold, and each name is an independent claim that FR-2 requires be answerable and that RS-7 records nobody owns re-checking. So the shrink that is actually justified is not "fewer names" but "no name the project cannot evidence" — which is Q-2's own rule, and is C-3. Fifteen names still cover all four classes.

**The whole-design tests.** Data over machinery: one tuple, one settings key, and the only new machinery is one reader and one overlay, each a copy of a shape shipped one task ago. Reuse an existing seam: `$before` + `_anchor_index` is used for exactly the case the comment at `sc:1084-1088` was written for, and `_merge`, `_compose`, `_filter_rules`, `load/save_settings` and `t()` are all untouched. Prefer deleting: nothing can be deleted here — the one deletion available (the `domain` + `.suffix` pairing) was already declined on measurement (RS-4). Diff plus what must be held: three definitions, one changed line in `generate_config()`, one command, six strings — and **two published contracts**, which is where the over-count sits. F-2 is therefore not a nitpick but the one place this design is larger than it needs to be, and it is larger in the dimension the clause tells us to count.

On dischargeability of C-4 — offered as evidence that the required property is satisfiable, **not** as a mandated design and not as this gate authoring stage 2's work: at least one element of the emitted array carries a key/value pair that is present in every settings state and every rule-set state and sits ahead of the reject rule's slot. Stage 4 (or a stage-2 round, if the PM prefers) picks the anchor; this gate only requires that whatever is published cannot vanish underneath a user's file.

## GC-2 — the rule-position override

**Substance: the override is right.** The emitted `dns.rules` has two kinds of member — rules that answer here and rules that choose a resolver — and `clash_mode` is a live user instruction about *path*, never about *whether*. Placing a name-scoped answer among the resolver-selection rules reproduces T-16's measured defect one task later with a privacy decision instead of an IPv6 one, and the probe settles it as a leak rather than as a mere non-block: at the field report's slot a listed name in `Global` and in `Direct` returned `NOERROR` with 1 record **and an upstream stub recorded the query**. `CONFIG_BASE`'s own comment (`sc:1138-1141`) records that this is why T-16's rule left the array. Nothing in the field report's slot buys anything back except the mode-as-escape-hatch reading, which is a worse escape than either of BC-14's because it also re-routes all of the user's traffic as a side effect.

**Authority: not this gate's to close.** `.harness/rules/25-decision-policy.md` has Mode 1 active and red line 4 — "conflict with an explicit user constraint, a stated 'don't…'" — always escalates, in all three modes, and no rubric can override it. The rule position was stated by the owner and is overruled by Q-6. That the goal sentence in `01` says "in every routing mode" resolves the *engineering* conflict but does not convert an owner constraint into an agent decision, because I cannot read the field report and cannot tell which of the two sentences the owner actually wrote. Hence C-11: proceed on the override, recommend keeping it, and surface it with the measurement attached. It is cheap to ask now and expensive to ask after `04`, `05` and both READMEs are written.

**Cost handling.** Stage 1 accepted the cost explicitly and BC-14/Q-11/FR-12 carry the two recourses into both READMEs, the changelog, the help row and `sc telemetry show`. What is missing is the sentence naming the cost itself — a user carrying the owner's original mental model will try `sc mode global` first, and nothing shipped tells them it will not help. T-16 wrote exactly that sentence for its own rule (`README.md:126`), so the precedent, the position in the document and the absence of a translation cost are all established. That is F-10/C-6 and it is the cheapest finding in this review to discharge.

## GC-3 — is FR-3's promise delivered end to end, and are V-28's classifications right?

**The promise is delivered.** V-22 observes a listed name and two depths of subdomain answered `NXDOMAIN` with `ANSWER: 0` through the real binary, timed, with neither stub recording the query; V-24 observes the same name resolving normally through a stub after `sc telemetry allow`, in all three modes, which is both the opt-out proof and the non-vacuity proof R-22's mirror image demands. So at least one criterion observes the behavioural goal and at least one observes its restoration — this is not T-15's failure shape. NFR-8/AC-B7 make the control mandatory rather than optional, and V-25's 24 comparisons against a HEAD clone cover the "did we change anything else" half.

**Classification walk, one by one.**
- **AC-B1 `[D]`** — correct: at HEAD a listed name is routed by the surviving chain to one of the two instrumented stubs and answered, never `NXDOMAIN`.
- **AC-B2 `[D]`** — correct: in `Global` the `clash_mode` rule (`sc:1136`) sends it to `remote_dns`, in `Direct` to `direct_dns`; both stubs are instrumented, both answer.
- **AC-B3 `[A]`** — correct, with one operational caveat worth stating in `04`: `sc telemetry allow` does not exist at HEAD, so the control is a plain HEAD generate-and-resolve (which *is* the `allow` document), not a HEAD invocation of the new command.
- **AC-B4 `[A]`** — correct: none of the four probe names is matched by the reject rule, nothing else in the document moves, and K-17's `.test` trap is honoured by V-25's own wording.
- **AC-B5 `[D]`** — correct, and correctly disjunctive ("resolves it **or** leaves it unanswered, never `NXDOMAIN`"). The second sub-case — the `proxy` outbound accepting and never answering — will stall ≈10 s per probe at sing-box's fixed deadline (insight-index line 24). That is exactly the shape T-16's gate caught, but here it is sound *because* the classification is `[D]` and defined negatively; the run must simply budget the time and must not read the stall as inconclusive.
- **AC-B6a `[A]`** — correct: `{"clash_mode": "Global"}` matches exactly one element at HEAD (T-16's V-5 measured both `clash_mode` anchors at one in both rule-set states), the user's own rule inserts, and HEAD rejects the user's name too.
- **AC-B6b `[D]`** — **wrong as written**, and this is F-1. At HEAD nothing in `dns.rules` carries `rcode: "NXDOMAIN"` — `_dns_overlay()` emits `"NOERROR"` (`sc:1581`) and no other rule carries an `rcode` at all — so `_anchor_index` finds zero matches and raises rather than the name "resolving anyway". The control is still a legitimate `[D]` (there is genuinely nothing to except at HEAD), but stated wrongly it invites QA to file the exception as inconclusive, which costs a round. C-1 corrects the text in place.
- **V-29 and V-30** are behavioural and outside V-28's enumeration (F-4). V-29's suppressed-AAAA half agrees at HEAD by construction — T-16 shipped that rule — so mapping it to a criterion classified `[D]` is the same contradiction T-16's F-1 named; V-29's unsuppressed half and all ten of V-30's probes are `[D]`. C-2 fixes the scope and the granularity.

## GC-4 — the membership audit, name by name

Fifteen rows pass FR-1's two clauses without qualification: N-1…N-6 (Microsoft diagnostics subtree, the two `vortex` hosts, `metrics.`/`daisy.ubuntu.com`, `incoming.telemetry.mozilla.org`), N-8…N-10 and N-12 (`google-analytics.com`, `app-measurement.com`, `crashlytics.com`, `scorecardresearch.com`), N-13, N-15, N-17 (`hm.baidu.com`, `mmstat.com`, `tracking.miui.com`) — each is a collection endpoint whose blocking loses reporting only, and the apex-vs-host calls are made on the right test (`telemetry.microsoft.com` as an apex because `watson.`/`oca.`/`sqm.` are all diagnostics; `data.microsoft.com` refused because `settings-win.` lives there; `umeng.com` refused because U-Push does). The exclusion table is real work, not decoration — `googletagmanager.com`, `analytics.google.com`, `omtrdc.net`, `clients2.google.com`, `connect.facebook.net`, the push and safe-browsing hosts, `doubleclick.net` and the attribution SDKs are each excluded on the second clause, and the two-member browser class is the honest consequence of applying it to Chrome rather than a gap to fill.

**RS-8's three.** The runtime downside really is bounded and one-directional — a name that does not exist rejects nothing — so this is not a safety question. It is a truthfulness question, and there `01`'s Q-2 is binding and unambiguous: "a name whose purpose cannot be evidenced at stage 2 is not shipped", with FR-2 requiring that "the list contains X because Y" be answerable for every member without running the tool. A host string nobody verified cannot satisfy that: if the string is wrong there is no endpoint whose purpose was evidenced, only a typo shipped in a curated artifact whose whole selling point is that it is auditable. Hence C-3's shape — corroborate the string cheaply at stage 4 (existence is enough; vendor and role are already firm) or drop, with a corrected spelling barred as a new member. My own doubt is strongest on N-7: the Firefox coverage ping is, to my recollection, submitted to a `coverage.telemetry.mozilla.org`-shaped host and the ping itself was retired, which is a reason to expect the check to fail — recorded here so stage 4 knows where to look, and *not* as authority to substitute a name.

**N-14 `cnzz.com` (F-7).** This one is not in RS-8 and should have been. Its second-clause clearance rests on the asserted claim that the site-owner console moved to `umeng.com`; that is the same class of claim that (correctly) excluded `analytics.google.com`, and the name certainly resolves, so the downside is *not* one-directional the way RS-8's is. It still ships, on three grounds: the collection role of the domain is firm and dominant in class 4, anyone affected is a site owner rather than the general user whose traffic this changes, and both BC-14 recourses reach them without a source edit. C-9 makes the comment state the test rather than only the payload, so a future re-audit (RS-7) has the claim to check rather than a conclusion to trust.

**N-11 `demdex.net` (F-8).** The Experience Cloud ID call on `demdex.net` is what Adobe Target's personalisation flow identifies against — the very coupling that excluded `omtrdc.net` — so blocking it can affect what a page renders. It survives the second clause because the denial is an immediate `NXDOMAIN` (measured ~4 ms, Q-A), so the client falls back at once instead of waiting out a pre-hiding timeout; that is a real dependence on I-4's *shape*, and a design that had chosen a drop or a sinkhole would have failed here. Worth one line in the comment (C-9), not a drop.

## GC-5 — routing RS-2

Three routes were available. **Rollback to stage 1** buys a corrected sentence at the price of a full round for zero behavioural change, and the decision it sits under (NXDOMAIN over empty NOERROR) is sound on semantics and unaffected — that is disproportionate. **Leave it as-is under K-12** is wrong in the other direction: `01` is archived and read by later tasks, and this pipeline has already demonstrated the mechanism — T-17's own stage 1 read T-16's Q-5 as an input. An unmeasured claim dressed as a measurement is precisely what NFR-10 exists to prevent, and leaving it would let a future task inherit it. **Amend at delivery** takes T-16's own precedent (its C-2 filed an AC amendment into `01` through the PM at delivery) and costs one edit. Hence C-7 — with the addition RS-2 missed: the same claim is in `01_RATIONALE.md` ("cached negatively for the whole name"), and an amendment touching only the contract's Q-5 would archive the rationale's copy intact (F-11).

## GC-6 — the `show` language tension

Stage 2 is right and the tension resolves without moving either document. Read FR-7 literally: `show` "additionally prints every name in the list, one complete line per name, in the user's language". The obligation attaches to the output; every part of the output that has a language — the setting line and the meaning sentence — is translated by Q-13's first three strings, and the part that does not have one is a domain name. FR-7 nowhere promises a per-name description; that reading is imported from K-9's alternative, not from the requirement. And the alternative is expensive in exactly the currency FR-13 makes binding: either untranslated English mid-list (NFR-2 calls that a correctness bug, citing R-19) or ~20 keys against a closed six-key budget. The justification the user actually needs is not per-line anyway — it is per-name evidence they read once, which FR-1/Q-2 place in both READMEs where mirroring makes it bilingual. C-9 keeps vendor and class there for every shipped name, which is what makes a user who sees a bare name in `show` able to find out why it is there.

- **The change ledger names `04_DEVELOPMENT.md`** (L-11) — the pipeline's fixed filename, no re-worded or suffixed variant anywhere in `02`.
- **RS-1's FR-10 report is accurate**: `$before` with an object anchor on an array `CONFIG_BASE` always defines carries the whole change, and the one thing not expressible (element addressing into a nested array) was already re-homed by Q-10. The directive vocabulary gains nothing.
