> Rationale portion for 03_GATE_REVIEW.md. Non-binding.

## 1. The owner's directive, tested rather than accepted

**What was claimed.** Option B — `except Exception` — is one word, needs no import, and is one line smaller than option A. The architect rejected it on the grounds that a genuine defect inside `clash_api()` would then be reported as `[PROBLEM] Clash API responding`, i.e. `sc doctor` lying about the host to cover a bug in `sc`.

**Test 1 — is the tuple complete over BC-1…BC-8?** Read from the installed stdlib, not recalled:

- `class URLError(OSError)` — `/usr/lib/python3.12/urllib/error.py:19`; `class HTTPError(URLError, …)` — `:35`. Both are already `OSError`, so BC-6 and BC-7 are covered and today's two names correctly *disappear* rather than move.
- `class HTTPException(Exception)` — `/usr/lib/python3.12/http/client.py:1511`; `IncompleteRead` `:1533`, `BadStatusLine` `:1559`, `LineTooLong` `:1566`, `InvalidURL` `:1519`, `RemoteDisconnected(ConnectionResetError, BadStatusLine)` `:1571`. `HTTPException` is a plain `Exception` subclass with no `OSError` and no `ValueError` in its bases, so BC-4 escapes any tuple that omits it — the architect's central claim, confirmed.
- `JSONDecodeError` is a `ValueError` and `UnicodeDecodeError` reaches `ValueError` through `UnicodeError`, so BC-2 and BC-3 are covered; `TimeoutError` is an `OSError` (and `socket.timeout` is an alias of it from 3.10, an `OSError` subclass on the 3.6 floor), so BC-1 is covered on every supported interpreter.
- BC-5 is not an exception at all — it is the `isinstance` gate — and BC-8 is the pre-existing `if text else {}`.

Every line citation in `02_RATIONALE.md` § "Grounding the exception set" resolves to the class it claims. The three-family tuple is complete over the requirement's stated boundary set.

**Test 2 — what escapes that `except Exception` would have caught?** Exactly `RecursionError` (a `RuntimeError`) from pathological nesting, `MemoryError` from pathological size, and any in-body `AttributeError` / `TypeError` / `NameError`. The first two are disclosed in the design's `## Out of scope` and belong to BC-12's already-lost threat model; the third is the purchase itself. Nothing escapes undisclosed. `KeyboardInterrupt` and `SystemExit` escape both options equally, which is correct — the 8 s egress wait must stay interruptible (`bin/sc:2558-2559` records the same reasoning for `cmd_doctor`).

**Test 3 — is the purchase real, or a preference dressed up?** Real, and it is *measurably* aligned with a published contract rather than with taste. I checked `README.md:268` verbatim: "`[UNKNOWN]` means the check could not run at all … never 'the thing being checked is broken'." Under option B an `AttributeError` in `clash_api()` becomes `[PROBLEM] Clash API responding`, which asserts the host is broken when `sc` is; under option A it reaches `cmd_doctor`'s isolation (`bin/sc:2555-2562`) and prints `[UNKNOWN] Clash API: this check could not run: …`, which is precisely what the README publishes. The architect's driver-versus-self-judging distinction is therefore not a rhetorical device: `cmd_doctor` cannot enumerate what an unknown probe raises, while a four-statement body can, and the project already wrote that position down at `bin/sc:2019-2022`. The cost is honestly counted at **net zero imports** (the `urllib.error` deletion pays for `http.client`), which leaves the true delta at roughly one line plus the docstring clause K-9 already requires.

**Ruling:** option A stands. The burden of proof was met. But the burden was met for the *code*, not for the *published surface* — see below.

**Test 4 — the published surface, where T-17's first application of this rule found its defect.** Two surfaces, judged separately:

- **K-7 (`docs/dev-map.md:39`)** — the row earns its extra lines: dev-map is the file the developer agent reads before writing code, and "callers add no `try`/`except`" is the one thing this task must stop a future reader from undoing (rule 70's adversarial check answers *yes*). But it states "never an exception" as an absolute that the same design document contradicts two sections later. That is a map and a code that will form two opinions the first time someone hits a pathological body — the exact failure mode `docs/dev-map.md` exists to prevent. F-5 / C-8.
- **K-8 (`CHANGELOG.md`)** — I checked house style: every `### 修复` bullet in this file is a long single paragraph enumerating what changed, what did not, and the upgrade path, so K-8's shape is in style and not bloat. Its defect is the opposite of bloat: it lists four commands and the file has **five** call sites. `sc mode`'s BC-1…BC-4 behaviour changes from a traceback to a printed `Route mode → <mode>` while the running process keeps its old mode, and `sc use`'s changes from a traceback to a config regeneration plus a service restart. Neither is in the bullet. F-3 / C-6.

## 2. R1 — ruling on BC-14, verified against the code

I reproduced the mechanism by reading rather than by trusting. `_doctor_clash()` (`bin/sc:2491-2510`) builds `rows = [(DOCTOR_OK, "Clash API", "127.0.0.1:%d" % port)]` **before** calling `clash_api()` at `:2503`; at HEAD BC-1…BC-4 raise out of that call, the local `rows` list is discarded with the frame, and `cmd_doctor`'s `except Exception` (`:2555-2562`) substitutes one `[UNKNOWN]` row for the whole section. `DOCTOR_EXIT = {0:0, 1:2, 2:1}` (`:2257`) then maps `UNKNOWN` to exit **2**. Under this design the same states return both rows, and `PROBLEM` (2) beats `UNKNOWN` (1) in `worst = max(...)`, giving exit **1** — but only when no other section already reports `PROBLEM`, which is why C-2 pins the qualified wording.

R1's analysis is correct. **Ruling: no stage-1 round.** Three reasons. (a) The change is already *entailed* by FR-2, which requires every one of those failures to become one no-answer result; BC-14 under-describes a consequence of a binding statement rather than contradicting it. (b) It cannot be avoided without a caller edit that AC-S2 forbids, so a reopened stage 1 would return the same design. (c) The gate document is itself binding on stages 4-7, so C-1 makes the widened statement authoritative at zero round-trip cost. Out-of-scope item 5 (F-10) is reconciled the same way: it means "this task designs no change to `sc doctor`", not "no observable of `sc doctor` may move".

**DEF-2.** T-05 shipped this open and named it exactly: `docs/features/_archived/sc-doctor/06_TEST_REPORT.md:344-346` and `07_DELIVERY.md:124-126` — "a *hung* Clash port loses S6's port row", predicted by that task's gate as F-12 before code was written and ruled acceptable. This design closes it as a side effect. **T-18 may claim it**, under C-3, because the claim is checkable by V6's BC-1 row pair rather than by argument. On ownership of the 2 → 1 move: `README.md:277-278` already publishes "1 = at least one `[PROBLEM]` — … an unanswered Clash API port" and lists no Clash-related cause under exit 2 other than "no port recorded in `settings.json`". So the design does not create a new user-visible contract; it moves the binary onto the contract the README already published, which is also why E8's "no README edit" conclusion is right — and stronger than E8 argues. The owner of the disclosure is the changelog bullet plus `07_DELIVERY.md` (C-1, C-2).

## 3. R4 — ruling on the miscount

Confirmed by search rather than by reading the design: `clash_api(` occurs at `bin/sc:1978` (the definition), `:2026`, `:2148`, `:2230`, `:2503`, `:2580` — **five** call sites. `sc ls` reaches the function through `stored_delays()` at `:2101`. ## 4. What I found that neither document caught

- **The third vacuity trap (F-7).** `CLASH_PORT` is a module global initialised to `CLASH_PORT_BASE` at `bin/sc:326` and reassigned by `main()` at `:3125` through `_resolve_clash_port()`. On a fixture whose `mkdtemp()` `settings.json` records no `clash_api_port`, `_resolve_clash_port()` calls `_free_port()` — which returns a port that is free **by construction** — persists it, and the whole BC-1…BC-8 matrix collapses to "nothing listening": the candidate prints `(unavailable)` everywhere and the control never tracebacks. It is K-11's twin in every respect, right down to `main()` being the reassigning frame, and NFR-5's control discipline is only a partial backstop (it catches the missing traceback, but only if QA reads its own control column). `_doctor_clash()` has the same exposure through `_saved_clash_port()`. C-9.
- **The two unenumerated call-site changes (F-3).** Read `cmd_use` `:2147-2153`: with `r is None` the run falls to `reload_or_restart()`, which regenerates `config.json` and calls `restart_service()`. For BC-1…BC-4 that path is newly reachable. It is the *right* behaviour — it is what a refused port does today — and K-10's `SYSTEMD = OPENRC = False` doubles as the safety control that keeps a fixture from restarting anything (C-11). `cmd_mode` `:2579-2581` discards the return value entirely, so those states now print a success line for a mode the running process did not adopt; again identical to today's refused-port behaviour, again unstated.
- **The bundled control inside BC-5 (F-2).** `json.loads("null")` yields `None`, so a `null` body is indistinguishable from a no-answer at HEAD *and* on the candidate: `(r or {})` gives `{}` and `sc status` prints `(unavailable)` in both. `5`, `"x"` and `[1,2]` are truthy non-dicts and do traceback. `.harness/insight-index.md:30` states this exact trap as a measured T-17 lesson — a control class is a property of an observation, never of a criterion — and BC-5 is a criterion bundling four observations with two different control classes. AC-B3 is otherwise the model application of that lesson: its eight states each carry their own declared class, which is why F-2 is a correction rather than a rebuild.
- **AC-B2's per-heading count (F-4).** `cmd_status` prints `=== Service status ===` then runs `systemctl status --no-pager -n 5` and `=== TUN interface ===` then `ip -br addr show` (`:2219-2225`). FR-3 is careful — it enumerates only the four facts — but AC-B2 and V7 generalise to "each of its section headings", which no run can satisfy. C-7 scopes it back to FR-3's four without weakening the observation.
- **The stand-in justification (F-6).** `BaseHTTPRequestHandler.wfile` is a raw binary stream, so state (c) is `self.wfile.write(b"\xff\xfe")` and state (d) is a `Content-Length` header larger than what is then written before close. Neither rules out `http.server`. The raw-socket server is still the better fixture because states (a) and (f) want socket-level control anyway, and one mechanism for eight states beats two — but QA must not read the sentence as forbidding the simpler thing.

## 5. Verified good — checked first-hand, no finding

- **The phantom stays dead.** `_egress_ip()` (`bin/sc:391-400`) is a docstring plus one `urlopen("https://api.ipify.org", timeout=8)`: no `ProxyHandler`, no `build_opener`, no `127.0.0.1`, no port. Its two call sites are `:2237` (inside `cmd_status`'s existing `try` / `except Exception`) and `:2520`. Nothing in the design reintroduces a fix for it: K-5 freezes the function *and* the surrounding handler, the frozen set names it first, and V1 verifies by AST extraction + sha256 rather than by grep, which is the right instrument because a `grep` for the endpoint literal would pass on a function that had gained a proxy argument.
- **BC-8 ordering.** K-3 is correct for a reason worth stating: the gate cannot break BC-8 because `{}` *is* a `dict`, so the only shape that could break it is a truthiness test — which K-3 forbids by name. The load-bearing line is `if text else {}`, and its removal is now silent rather than loud (PA-1).
- **Safety.** The re-exec at `bin/sc:116-117` fires only when `os.geteuid() != 0`, so `sudo python3 <repo>/bin/sc status` never reaches `/usr/local/bin/sc`; `_init_files()` (`:462-473`) is `mkdir(exist_ok=True)` plus two `if not …exists()` branches, all no-ops under V7's preconditions; `_resolve_clash_port()` (`:364-388`) returns the saved port **before** any write when one is recorded. V5's mutating `PUT /proxies/proxy` is routed to the stand-in explicitly in two places (the stand-in paragraph and the frozen set). NFR-3's mtime + size witness is what converts those four readings into evidence; C-12 adds the one thing missing — that a **false** precondition aborts the run rather than degrading it into an artifact check, because an unrecorded `clash_api_port` would make `sc status` itself write to `settings.json`.
- **Q-13, red-line-adjacent.** Ruled **permitted**, on the owner's standing grant and the T-17 precedent, not blocked: the invocation is read-only by four independent code paths I checked myself, it is bounded by five preconditions and a before/after witness, and R-22 exists precisely because T-15 shipped 35 green criteria while the promise stayed materially wider than the behaviour. Removing AC-B1/AC-B2 would reproduce that failure exactly. The decision is surfaced here so `07_DELIVERY.md` can carry it explicitly.
- **Verify_all and the baseline.** Nothing in the permitted diff (`bin/sc`, `docs/dev-map.md`, `CHANGELOG.md`, stage docs) touches a `verify_all` input other than B.1's syntax check and F.6's per-doc cap. One trap worth naming: E.6 scans **every** `docs/features/**/06_TEST_REPORT.md`, not only archived ones, so the FAIL lands the moment QA writes its report with a numbered heading — hence C-13 despite NFR-7 already saying it. `.harness/insight-index.md` is at exactly its 30-line cap and `docs/tasks.md` at its 300-line cap, so the risk is not in this task's diff at all but in what the PM appends afterwards (C-14).
- **Rule and schema compliance.** `.harness/rules/70-doc-size.md` carries no `## Stage-doc boundary rule` section in this project, so per the contract the declared schema is applied as written and this review proceeds — Q-12's ruling, re-checked. `.harness/agents/` contains no files, so `02`'s single-developer partition assignment is correct against `.harness/rules/50-singbox-cli.md` § Partitioning. NFR-1's floor is untouched: `import http.client` is stdlib and 3.6-clean.

## 6. Why the verdict is not a rollback

Dimension 7 fails, and a failing dimension normally forecloses approval. It does not here, for a reason I want on the record rather than implied: every one of its causes is a **statement about how a later stage observes**, not a decision about what gets built. F-4 is a criterion's scope, F-1 and F-2 are two expectation cells in a verification table, and F-7 is a fixture constraint. None of them changes a line of `bin/sc`, the choice between options A-E, the frozen set, or the permitted diff. A stage-1 or stage-2 round would return the same design with three cells edited, and it would cost the batch a full re-review of two documents that are otherwise the most precise this project has produced. The binding-conditions table is the declared instrument for exactly this, and C-5, C-7 and C-9 are each checkable by reading `06_TEST_REPORT.md`. If stage 6 discharges them and the observations still do not separate candidate from control, that is the point at which the requirement — not the gate — has to be reopened.
