## Pre-answered developer questions

| id | question | answer |
|---|---|---|
| P-1 | `sc reload` on an unusable `settings.json` prints two nearly identical `Cannot use …` lines — is one of them a bug I should remove? | No. `main()` calls `_load_lang()` on **both** arms (`bin/sc:3754-3758`) → `:398-401` → `:610-611`, so every command writes the announcement; `main()`'s envelope writes the refusal (`:3786-3788`). Both render the same translation key by design; AC-1 permits and does not count the first. Removing either is out of scope (K-4, C-8, C-11). |
| P-2 | Should `save_settings()` become atomic, or route through `_write_private()`, while I am editing it? | No. `_write_private()` is T-13's single definition of installing a **credential** document and `settings.json` is not one (it is `0644` on every default install); K-3 / Q-9 forbid a second writer, a mode change and an atomicity guarantee. A part-way write leaving a truncated document is BC-5 — stated, and reported by name on the next run. |
| P-3 | Is `except SystemExit:` at `bin/sc:451` dangerous — can it swallow an exit the run actually needed? | No, as long as the `try` keeps exactly one statement. `save_settings(settings)` is the only statement in that block (`bin/sc:449-452`), and after I-1 the only `SystemExit` it can produce is the one its own handler raises. Adding any statement to that `try` breaks the argument. |
| P-4 | `generate_config()`'s new `load_settings()` statement discards its value — may I bind it, or move it above the override wrapper to fail earlier? | Discarding is intended. Moving it is forbidden by K-2: the comment at `bin/sc:2049-2052` states the override is parsed first, and the override must keep precedence in the reported cause when both documents are unusable. |
| P-5 | On an unusable `settings.json`, `sc add` still writes `nodes.json` before the refusal — is that a bug to fix? | No. BC-13 rules it: a node-store write already performed stands and is not rolled back, exactly as a service action already taken stands. The refusal's job is to stop `config.json` being replaced, not to unwind the command. |
| P-6 | E-10's re-raise arm ends the run with no run-level outcome line — should I print the outcome block before re-raising, so the run always states what it did to the service? | No. That is the escalation the design pre-specified and deliberately left unspent, it would render an outcome for documents out-of-scope 7 excludes, and HEAD prints none on those paths either (`bin/sc:3396` is above `:3410-3420`). AC-19 admits both arms on purpose; the shortfall is a HEAD property filed under C-12, not work for this task. |
| P-7 | The new assertions live in `.harness/scripts/` — does `verify_all` A.1 protect me from committing a credential-looking literal there? | No. A.1's pathspec excludes `.harness/*` wholesale and its regex is case-sensitive (insight index, 2026-08-16), so nothing you add to `check-sc-contracts.py` is scanned. NFR-7 is held by the artifact itself, and none of I-5 / I-6 / I-7 needs a credential: they use a source scan, a `[]` document, a non-existent parent directory and a lone surrogate. Use no credential-shaped literal at all. |
