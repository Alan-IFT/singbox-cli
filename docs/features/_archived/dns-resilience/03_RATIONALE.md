## 1. Is the surviving task still coherent, and does it belong with T-17?

Applied `.harness/rules/85-design-discipline.md`'s three tests to what is left after two rounds of subtraction.

**Patch-then-patch seam.** T-16 computes nothing that only T-17 consumes. Its outputs — a suppression rule at `dns.rules[0]`, a persisted setting, a command, a corrected fault attribution — are each user-visible on their own the day they ship. The intermediate-state clause is the one that matters here, and it is satisfied *conditionally*: the shipped state is honest only if the user-facing text claims no more than the measurements support. That is precisely what K-16, V-21 and RS-9 exist for, which is why C-3 and C-10 tighten them rather than leaving them to good intentions. Without those, a task whose batch row promises "a non-proxied fallback resolver, converge the 10s DNS timeout" and ships neither would be exactly the dishonest intermediate state rule 85 forbids.

**Duplicated judgment.** T-17 needs no IPv6 decision and no notion of a node-independent class; it needs a position in `dns.rules` for a reject rule. That position remains expressible, and the design proves it rather than assuming it — V-5 checks that the `{"clash_mode": "Direct"}` anchor still matches exactly one element after the prepend, which is the one property `_anchor_index` (`bin/sc:1182-1202`) needs and the one a careless insertion would break. Nothing is decided twice across the two tasks.

**Shape check.** The design is shaped around one judgment (`ipv6_decision()`), one carrier (`_dns_overlay()`) and one document key, not around the batch row's three-symptom list. Two of the three symptoms turned out to be capabilities the software lacks; the response was to delete them and state the limit, not to build a shape that mimics them.

So: no merge with T-17, and nothing half-built. What *would* have been half-built — the catch-all plus a re-pointed `final` — is exactly what round 2 removed, and the measurements show it would have read like a guarantee while delivering nothing on the failure path. Deleting it was the coherent move, not a retreat.

The one thinness worth naming: T-16's own contribution to the node-independent class is precisely `dns.rules[0]`. The design says so in I-17 rather than dressing HEAD behaviour up as new delivery, and it then commits to *proving the preservation* of `[1]` and `[6]` (V-26 … V-28, V-32, V-34). That is the honest framing, and it is a large part of why I am approving.

## 2. FR-8's new formulation, checked against the real code

I rebuilt I-17's index mapping from `bin/sc:1097-1107` rather than accepting it. HEAD's array is `[0]` `hosts_dns`, `[1]` `clash_mode: Global` → `remote_dns`, `[2]` `clash_mode: Direct` → `direct_dns`, `[3]` `query_type [64, 65]`, `[4]` `geosite-google`, `[5]` `geosite-private`, `[6]` the five `domain_suffix` names, `[7]` `geosite-cn`. Deleting `[3]` and `$prepend`ing one rule yields exactly I-17's list. The `rule`-mode class (`[0]`, `[1]`, `[6]`), the `global` narrowing (`[2]` captures the rest by the user's own instruction), the `direct` widening (`[3]` sends everything else to `direct_dns`) and the degraded survivor set (`_filter_rules` at `bin/sc:879-881` keeps every rule with no `rule_set` key, so `[0]`, `[1]`, `[2]`, `[3]`, `[6]` survive) are all correct as stated.

Node-independence of `direct_dns` I checked on two mechanisms, not one. `direct_dns` (`bin/sc:1086-1087`) carries no `detour`, and `route.rules[0]` (`bin/sc:1121`) sends sing-box's own process direct ahead of both `clash_mode` route rules — so in production the re-entrant TUN path cannot route a DNS dial through `proxy` in any mode. In the behavioural fixture the TUN inbound is gone, so that mechanism is not the one under test; the fixture's `direct_dns` dial simply never touches the `proxy` outbound. Both give the same answer, but they are different mechanisms, which is why F-10/C-11 asks stage 6 to say so out loud instead of letting a green report imply the shipped path was measured.

One detail I verified because the design leans on it: `remote_dns` carries a **server-level** `domain_resolver: hosts_dns` (`bin/sc:1084`), so answering AAAA at index 0 — ahead of the `hosts_dns` rule — cannot break the DoH bootstrap. The rationale's claim is correct.

**Ruling on the unmeasured `hosts_dns` semantic (R-1).** It may be settled at stage 4/6; it does not have to be settled before code is written. Three reasons. (a) No code path depends on the answer: `_dns_overlay()` emits the same rule either way, and the emitted document is identical whichever semantic holds. (b) The only artefact that would be *wrong* if R-1 fired is the README's statement of the class — and that artefact is written in the same stage as the measurement, so C-3 orders them: the measurement first, the sentence after. (c) The existing field evidence is already strong: the host's hand-patch to the index-3 rule produced a measured 10.0 s → 0.016 s change, which is impossible if rule 0 terminated the chain, and the whole rule-set split routing works in production for the same reason. Blocking code on a semantic that is already excluded by production behaviour, and that no code decision turns on, would be gate theatre.

## 3. RS-10 — the ruling the architect asked for, and why the correction is made here

I verified the claim before ruling on it. At HEAD, an AAAA query under clash mode `direct` matches `{"server": "direct_dns", "clash_mode": "Direct"}` (`bin/sc:1100`) — `direct_dns` is `119.29.29.29` over UDP with no `detour` — so it is answered by a resolver that no node touches, and cannot stall no matter what the node does. Under `global` the same query matches `{"server": "remote_dns", "clash_mode": "Global"}` (`bin/sc:1099`), and `remote_dns` carries `detour: proxy` (`bin/sc:1085`), so it does stall at sing-box's own 10.0 s deadline. The architect's reading is exactly right, in both halves.

**Decision: the text is amended now, by this gate's C-2, and not by a third requirement round.** Reasoning, in the order that decided it:

1. *Leaving it to stage 6 is the worst option.* A QA agent bound to AC-B10's literal text would run V-31, observe no stall in `direct`, and be forced by NFR-7 to report **inconclusive** — or, worse, to reinterpret the AC quietly. Quiet reinterpretation at stage 6 is the R-22 failure mode wearing a different hat. Anything that leaves a known-false clause standing until after implementation is choosing the failure this whole task was reshaped to avoid.
2. *A rollback to stage 1 buys nothing this gate cannot deliver.* The correct text is fully determined by a fact already measured and re-verified by me in the file; there is no judgment left for the analyst to exercise, no other requirement line moves, and no design or code consequence follows. A third stage-1 round would re-review a 300-line document to change one clause, and would take the rollback streak to 2 of 3 for a text edit.
3. *A gate condition is the designed instrument for exactly this.* `APPROVED WITH CONDITIONS` means "conditions listed, must be met during development". C-2 states the corrected clause in full, names the stages bound by it, and names the PM as the one who folds it into `01` at delivery — which is where RS-10 was already routed. The correction does not author a new requirement; it repairs an internal contradiction between an acceptance criterion and a measurement the same document already records.
4. *The substance survives intact.* AC-B10's real content is "every behavioural run has a HEAD control, and a defect control must exhibit its defect". In `direct` mode the defect at HEAD is the **absence of suppression** — the AAAA query is issued to a non-proxied resolver and answered — and V-31 observes precisely that. The control still fails loudly if the candidate accidentally ships HEAD behaviour, which is the property that matters.

I want the limit of this instrument on the record: I would not have used a condition if the correction had required re-deriving anything, if it had touched the code, or if the corrected text had been a matter of judgment rather than of a measured fact. C-2 and C-4 are the only two conditions that reach into `01`, both are scoping corrections of over-statements, and both are filed back into `01` at delivery so the document does not stay wrong.

## 4. Would these 34 criteria catch a T-15-style gap?

R-22's pattern is: 35 green criteria, none of which observed the goal, and a promise materially wider than the behaviour. I tested T-16's set against the question "could a candidate emit exactly the right document, deliver no user-visible improvement, and still pass everything?"

The answer is **no**, and the reason is structural rather than lucky. AC-B4/V-29 times a real AAAA query through a real sing-box with a node that accepts and never answers, and its HEAD control must show the ≈10 s stall — a candidate that emitted the right JSON but did not actually suppress would fail it, and a fixture too weak to reproduce the defect would be reported inconclusive rather than passing. V-36 closes the vacuity hole that AC-B4 alone would have had: with an unreachable upstream, "issues no upstream query" is trivially true, so a usable-node run is required to make the observation real. That single step is the clearest evidence that the R-22 lesson was actually absorbed, and it was added by the architect rather than the analyst — the independent perspective paying for itself.

The rest of the set is honest about what it is: AC-B1 … AC-B3, AC-B9 observe the preserved class with real hung and refusing nodes; AC-B7 observes resolver assignment per name across 36 combinations against a HEAD clone; AC-B8 observes that the unmatched class did not silently migrate to the non-proxied resolver — the one outcome Q-17 traded FR-8 away to protect, and the one a careless "fix" would have produced.

Two things keep it from being unqualified, and both are conditioned rather than waved through:

- **The defect/agreement split has two holes, not one.** RS-10 caught the `direct`-mode control. It did not catch that V-26's third probe (AAAA of an unmatched name) makes AC-B1/AC-B2/AC-B3/AC-B9's HEAD controls stall ≈10 s while AC-B10 classifies them as *agreement* controls that must reproduce the candidate's outcome. That is F-1. The repair is a one-word change — the probe becomes type 64 or 65, which HEAD already suppresses at `bin/sc:1101`, making the control genuinely an agreement control while still exercising "the suppression rule answers this class". The type-28 observation belongs where AC-B10 already puts it, in the defect-reproducing rows. Left unfixed, four behavioural runs would come back inconclusive under NFR-7 and someone would be tempted to explain them away.
- **Three structural steps carry a witness that cannot fail.** F-5. Under NFR-6's mandatory `SYSTEMD = OPENRC = False`, `restart_service()` (`bin/sc:1609-1613`) calls nothing, so "the shims record no invocation" is true no matter what the code does — and V-15's *positive* claim "the service is restarted once" cannot be observed at all. V-14's `config.json` mtime clause does carry AC-13 on its own, since `reload_or_restart()` regenerates before restarting, so the criterion is salvageable; but a witness that cannot fail is the same species as R-10's `grep` prefix, and the design caught one instance and not the other. C-6 makes the witness one that can fire, with V-15 as its own non-vacuity control.

## 5. Scope honesty, and whether the docs as specified leave a true picture

K-16 + V-21's grep + RS-9's filed row are sufficient in kind: they forbid the claim, check for it mechanically, and carry the shortfall to delivery instead of letting a green report imply the batch goal was met. Two gaps in degree, which C-3 and C-10 close.

First, the README's statement of the node-independent class (L-12) is the most consequential sentence this task ships — it tells a user which names keep working when a node hangs — and as specified it may be written from I-17's *predicted* mapping. If R-1 fires, the sentence is wrong in the direction that matters (promising more than is delivered), and nothing in the plan orders the measurement before the sentence. C-3 orders them.

Second, BC-14 tells a user that a node reachable only over IPv6 becomes unreachable under suppression, and RS-3 says the mechanism is unverified because `route.default_domain_resolver` (`bin/sc:1118`) pins dial-side lookups outside `dns.rules`. Nothing observes it. L-12's list does not include BC-14, so no over-claim currently ships, but the requirement carries the assertion and any of the three remaining stages could pick it up in good faith. C-10 fences it.

With those two, a user reading the shipped READMEs would get a true picture: what is answered without a node, in which mode, in which rule-set state; that a proxied resolver which does not answer produces no answer and no second attempt; and no sentence anywhere implying a fallback or a wait this build does not have.

## 6. Fixture feasibility and risk

This is where the time will go, and the plan is better prepared than most: the PM's probe already built a near-identical fixture successfully, which is the strongest possible evidence that the derivation is buildable, and its two hard-won prerequisites are promoted to binding constraints (K-15 — `{"action": "sniff"}` at `bin/sc:1122` ahead of `hijack-dns` at `bin/sc:1123`, and `route.default_domain_resolver` at `bin/sc:1118` kept or 1.13.15 fails `check`). K-14's "both servers are local stubs, node state staged at the `proxy` outbound" is what makes the 100 ms number a property of the document rather than of the network, and it is correct.

The gap is F-6. `remote_dns` is `type: https` — a DoH server (`bin/sc:1085`). Standing it up locally means either a TLS-terminating stub sing-box will trust, or changing the transport, and the plan's own sentence ("three derivations of the emitted document, and no fourth") forbids the second without saying it has chosen the first. This is not a design error so much as an unstated decision that stage 4 will hit within the first hour, and it interacts with M-5's explicit non-result (a detoured DoH server was never measured against the plain-UDP path). C-7 requires the decision to be declared, counted, and its limits recorded — and requires the recipe, including the staged shape of the `proxy` outbound for each of the three node states, to be pasted into `04` verbatim, since stage 6 must rebuild it independently and nothing is committed to the repository (R-9 owns a committed harness, not this task).

## 7. Standing safety constraints — verified, not assumed

- **Import-time auto-elevate.** NFR-6 mandates the `docs/dev-map.md:107-137` recipe verbatim, which neutralises the *sudo re-exec* by shimming `os.geteuid` rather than editing `bin/sc`, and fails closed if `geteuid` moves. That is the right recipe, and it is the one that keeps the hand-patched `/usr/local/bin/sc` out of the picture entirely. NFR-6 additionally forbids invoking `/usr/local/bin/sc` at all.
- **`_init_files()`.** Never driven (NFR-6, K-10). I confirmed why it matters: `bin/sc:421` hard-codes `Path("/var/lib/sing-box")`, the one directory not built from a repointable constant. This is also the constraint that produced F-4 — the reason `sc ipv6 show`'s write-freedom cannot be demonstrated at the command level is precisely that driving `main()` would drive `_init_files()`. The constraint is right; the acceptance criterion written against it was not.
- **Live service and `/etc/sing-box/`.** Eight path constants repointed into one `mkdtemp()` root **and asserted so** — assertion rather than vigilance, which is the lesson from the earlier incident. `IF_INET6_PATH` (I-1) is added as the eighth precisely so AC-16/AC-17 need no root; that is a genuine testability gain, not incidental.
- **Service witness.** `systemctl show sing-box -p MainPID -p ActiveEnterTimestamp` at every checkpoint, never `is-active`. Correct, and it is the witness that would have caught the T-02 incident. Note this witness proves the *live* service was untouched; it is not the witness for "did the fixture restart" — that is F-5/C-6, a different question that the design conflated with shims that cannot fire.
- **Clash API.** No `PUT`/`PATCH`/`DELETE` to the live controller; V-31 drives the *fixture* instance's own API on its own port. Both `01` (AC-B6) and `02` (V-31) say "fixture instance", consistently. Every second sing-box runs unprivileged, with no TUN inbound, its own `cache_file.path` and its own Clash port.

I found no violation of any of the four constraints in the verification plan as written.

## 8. Verdict vocabulary, and why `APPROVED WITH CONDITIONS`

The dispatch names `APPROVED FOR DEVELOPMENT`, which is the plan-mode string; the task is unambiguously full mode (`PM_LOG.md` header, seven stages, stage 4 dispatched on approval), so the full-mode vocabulary applies and the mode is not in doubt — `BLOCKED ON MODE UNCLEAR` would be wrong. Between the two full-mode approvals, plain `APPROVED` would be false: dimension 7 is a FAIL and eleven conditions must be met. `APPROVED WITH CONDITIONS` is the accurate string and carries the same routing consequence the dispatch expects — the PM dispatches stage 4.

On the FAIL coexisting with an approval: the alignment rule forbids `APPROVED` alongside a FAIL, and I am not issuing it. I marked dimension 7 FAIL rather than WARN deliberately, because the question that dimension asks — "any criterion that's unverifiable?" — has the answer "three, as written", and softening that to WARN would be the same narrowing this task exists to stop doing. What makes the approval nonetheless right is that all three defects are text-level, none touches the code, none requires an upstream re-derivation, and each is repaired by a condition whose corrected text is stated in full and whose discharge is observable in `06`.
